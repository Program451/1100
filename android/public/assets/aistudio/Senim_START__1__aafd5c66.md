## Как читать этот документ (обязательно)

1. Это единый стартовый документ для всех нейросетей проекта Senim. Владелец проекта присылает тебе его вместе с короткой фразой «Твоя роль: N».
2. Выполняй ТОЛЬКО раздел своей роли (Часть 2). Остальные роли читай как справку о стыках. Код чужих ролей не пиши.
3. Часть 1 (общий блок) обязательна для всех. Контракт нельзя менять самовольно: если считаешь, что его надо изменить, объясни почему и предложи правку.
4. Первый ответ: одной строкой подтверди роль; перечисли не более 5 несостыковок или пробелов, которые нашёл в контракте (или напиши «несостыковок нет»); затем выполни шаг 1 своей роли.
5. После каждого шага остановись и жди слова «дальше». Не делай несколько шагов сразу.
6. Если чего-то не хватает, возьми значение по умолчанию из контракта, запиши допущение одной строкой и продолжай. Не задавай больше одного вопроса за раз.
7. Отвечай по-русски. Код давай полными файлами, с путём файла в начале. Комментарии в коде на русском в сложных местах.
8. Не выдумывай ключи, пароли и реальные данные государственных органов. Реальные ключи берутся из переменных окружения.

## Приоритеты: что делаем и что нет

- ОБЯЗАТЕЛЬНО (ядро, должно работать безупречно): проверка ссылок и предупреждение; тревога доверенному лицу (push + запасной опрос); демобанк с отменой перевода; правила риска на сервере.
- ЖЕЛАТЕЛЬНО (после ядра): локальная модель распознавания мошеннической переписки (требование владельца: работает только на телефоне, текст не уходит с устройства; запасной вариант на правилах обязателен), проверка номеров, проверка звонящего при входящем звонке (уровень 1), проверка ссылок из переписки, тестовый Telegram-бот и встроенный тестовый чат как источники сообщений, «привратник» для ссылок, код-приманка, подсказка при видеозвонке.
- БОНУС (только если ядро уже работает): проверка файлов по хешу, офлайн-журнал, анализ разговора на телефоне (уровень 2, только демо с проигрыванием записи).
- НЕ ДЕЛАЕМ В КОДЕ (только слайд «Развитие»): распознавание и хранение лиц, реальные данные государственных органов, блокировка перевода без участия банка.

ПРОЕКТ: Senim — защита клиентов банков от телефонного и интернет-мошенничества. Хакатон, 5 дней, разработчик один.

ЯДРО ПРОТОТИПА:
1) Подозрительная ссылка приходит в уведомлении WhatsApp/Telegram (Android), приложение проверяет её и показывает предупреждение.
2) Тревога близкому: если пользователь закрыл депозит и готовит крупный перевод новому получателю, второй телефон (доверенное лицо) получает push «Возможно, вашего близкого пытаются обмануть. Позвоните сейчас». Доступа к деньгам у доверенного лица нет.

5a) Источники сообщений: уведомления (Telegram, WhatsApp), тестовый Telegram-бот и встроенный тестовый чат приводятся к одному виду и идут в один конвейер: окно 10 сообщений, затем ScamClassifier, затем проверка номера и ссылок. Ссылки из сообщений любого источника извлекаются на телефоне и отправляются на проверку (только адрес, без текста). В собственном интерфейсе Senim (бот, тестовый чат) ссылка неактивна, пока проверка не завершена.
5b) Звонки: при входящем звонке с номера не из контактов Senim сверяет номер с базой жалоб и показывает предупреждение на экране (уровень 1, без прослушивания). Бонус для демо (уровень 2): по кнопке «Защита разговора» с согласием пользователя речь распознаётся на самом телефоне и оценивается той же локальной моделью. Родственникам отправляется только вывод, а не содержание разговора.
6) «Привратник» для ссылок: Senim открывается как обработчик ссылок, ссылка сначала проверяется на сервере, и только потом открывается в браузере.
7) Необязательный этап: проверка файлов по хешу (SHA-256) через пункт «Проверить в Senim».
7a) Подсказка при видеозвонке: если видеозвонок идёт с номера не из контактов, Senim показывает уведомление-памятку (попросить провести рукой перед лицом и повернуть голову, назвать семейное кодовое слово, перезвонить самому по известному номеру). === 1. ОБЩИЕ ПРАВИЛА (нарушать нельзя) ===
- JSON-поля в snake_case. Время: ISO 8601 UTC, например 2026-11-25T10:30:00Z.
- Деньги: целое число в тенге (50000, не 500.00). Валюта всегда KZT, поле валюты не передаётся.
- ID пользователей (user_id): строка из тестовых данных, например user_mom, user_son. НЕ UUID.
- ID всех остальных объектов (transfer_id, alert_id, record_id): UUID v4, строкой в нижнем регистре, создаёт клиент (приложение).
- Авторизации в прототипе нет: user_id передаётся в теле или параметре запроса. Это только для демо, в продукте нужна авторизация.
- Работай только в своей папке. Если нужно изменить API, предложи правку контракта, а не меняй формат самовольно.

=== 2. СПИСКИ ЗНАЧЕНИЙ ===
- alert_type: suspicious_link, deposit_closed, new_recipient, decoy_used, suspicious_call.
- Статус перевода (status): pending, completed, cancelled, flagged.
- Роль устройства (role): user, trusted.
- Сигналы риска (signal_type), которые сервер запоминает за окно времени: link_high, number_high, file_suspicious.
- Признаки текста (pattern_flags), определяет только телефон: family_claim_new_number (просьба вроде «Мама, это я, у меня новый номер»), urgent_money_request (срочная просьба о деньгах), asks_code (просят код из SMS), asks_screen_share (просят показать экран).
- Вердикт файла (verdict): clean, suspicious, unknown.
- Коды ошибок: INVALID_SIGNATURE, LIMIT_EXCEEDED, CHAIN_BROKEN, REPLAY, NOT_FOUND, VALIDATION_ERROR, INVALID_STATE.

=== 3. ПРАВИЛА БИЗНЕС-ЛОГИКИ (настройки сервера, значения по умолчанию) ===
- RISK_WINDOW_MINUTES = 30: окно, в котором сравниваются события.
- RISK_AMOUNT_THRESHOLD = 100000: порог суммы перевода в тенге.
- RISK_AMOUNT_THRESHOLD_WITH_SIGNAL = 50000: сниженный порог, если в окне уже есть сигнал риска (link_high, number_high или file_suspicious).
- TRANSFER_PENDING_SECONDS = 120: перевод остаётся pending и может быть отменён, затем становится completed автоматически.
- DECOY_TTL_SECONDS = 300: срок жизни кода-приманки.
- «Новый получатель» = to_account, на который этот user_id ещё не переводил.
- Тревогу создаёт ТОЛЬКО сервер, никогда приложение. Условие: в окне RISK_WINDOW_MINUTES было закрытие депозита, затем перевод новому получателю на сумму >= RISK_AMOUNT_THRESHOLD. Сигналы link_high, number_high и file_suspicious сервер запоминает и учитывает: при наличии хотя бы одного сигнала в окне порог суммы снижается до RISK_AMOUNT_THRESHOLD_WITH_SIGNAL. Сигнал сам по себе тревогу не создаёт, предупреждение при этом показывается только самому пользователю. Событие decoy_used создаёт тревогу сразу.
- При тревоге перевод получает статус flagged (его по-прежнему можно отменить).
- CALL_ALERT_SCORE = 0.85: порог local_score для тревоги по анализу разговора (уровень 2).
- Тревога suspicious_call создаётся сразу, если номер звонящего в базе жалоб (channel=call) или local_score >= CALL_ALERT_SCORE при channel=call_transcript. Исходный перевод она не блокирует.
- Текст push фиксирует сервер: «Возможно, вашего близкого пытаются обмануть. Позвоните сейчас». Для suspicious_call текст другой (человек на линии): «Возможно, вашему близкому сейчас звонит мошенник. Напишите ему или перезвоните после разговора».

=== 4. КОНТРАКТ API (v1) ===
Базовый URL: http://<IP-ноутбука>:8000 (см. раздел 6). Все запросы и ответы: JSON, UTF-8.
- POST /demo/reset  сбросить демо-данные к начальным (только для демо)  ответ: {"status": "ok"}
- POST /devices/register  тело: {"user_id", "fcm_token", "role", "public_key" (необязательно)}  ответ: {"status": "registered"}  (приложение вызывает при запуске и при смене токена)
- POST /trusted-contacts  тело: {"user_id", "trusted_user_id"}  ответ: {"status": "ok"}
- GET  /trusted-contacts/{user_id}  ответ: {"user_id", "trusted_user_ids": ["..."]}
- POST /links/check  тело: {"user_id", "url", "source": "notification|telegram_bot|demo_chat|gatekeeper", "sender_key": "..." (необязательно)}  ответ: {"risk": "low|high", "reasons": ["..."]}  (url нормализованный, см. раздел 11; при high сервер запоминает сигнал link_high и, если передан sender_key, связывает его с отправителем)
- POST /numbers/check  тело: {"user_id", "phone_hash", "sender_kind": "phone|telegram" (по умолчанию phone), "channel": "message|call|call_transcript" (по умолчанию message), "in_contacts": false, "pattern_flags": ["..."], "local_score": 0.0 (число 0..1 от локальной модели, необязательно)}  ответ: {"risk": "low|high", "reasons": ["..."], "sources": ["complaints"]}  (sources: какие источники сработали; phone_hash = SHA-256 нормализованного номера, например от строки "+77000000001"; при high запоминается сигнал number_high)
- POST /numbers/report  тело: {"user_id", "phone_hash"}  ответ: {"status": "ok"}  (пользователь отмечает номер как мошеннический, пополняя базу жалоб)
- POST /files/check  тело: {"user_id", "sha256", "file_name", "size_bytes", "source_app"}  ответ: {"verdict": "clean|suspicious|unknown", "reasons": ["..."]}  (необязательный этап; сам файл на сервер не отправляется; при suspicious запоминается сигнал file_suspicious)
- GET  /accounts/{user_id}  ответ: {"user_id", "balance", "deposit_balance"}
- POST /deposits/close  тело: {"user_id", "amount"}  ответ: {"status": "closed"}
- POST /transfers  тело: {"transfer_id", "from_user_id", "to_account", "amount", "created_at"}  ответ: {"transfer_id", "status"}
- POST /transfers/{transfer_id}/cancel  ответ: {"transfer_id", "status": "cancelled"}  (доступно, пока статус pending или flagged, иначе 409 INVALID_STATE)
- GET  /alerts?user_id={trusted_user_id}&since={ISO8601}  ответ: {"alerts": [Alert]}  (запасной канал, если push не дошёл: приложение доверенного лица опрашивает раз в 5 секунд)
- POST /decoy/issue  тело: {"user_id"}  ответ: {"decoy_code", "expires_at"}
- POST /decoy/use  тело: {"user_id", "code"}  ответ: {"valid": false, "alert_raised": true}
- POST /offline/reserve  тело: {"user_id", "amount"}  ответ: {"reserved", "limit"}
- POST /offline/sync  тело: {"user_id", "device_id", "records": [OfflineRecord]}  ответ: {"accepted": ["record_id"], "rejected": [{"record_id", "code"}]}

Модель Alert: {"alert_id": UUID, "alert_type": string, "about_user_id": string, "about_user_name": string, "transfer_id": UUID или null, "message": string, "created_at": ISO8601}
Push (FCM data message) = тот же объект Alert, все поля строками.

=== 8. OFFLINE RECORD (формат записи офлайн-журнала) ===
{ "record_id": UUID, "device_id": string, "counter": int (с 1, без пропусков), "prev_hash": hex, "from_user_id": string, "to_user_id": string, "amount": int, "created_at": ISO8601, "signature": base64 }
Строка для подписи (строго в таком порядке, разделитель |):
record_id|device_id|counter|prev_hash|from_user_id|to_user_id|amount|created_at
Подпись: Ed25519 над этой строкой в UTF-8 (если Ed25519 недоступен на устройстве, перейти на ECDSA P-256 по согласованию, изменение вносится в контракт для всех).
Хеш записи: SHA-256 (hex) от строки для подписи + "|" + signature. prev_hash первой записи: 64 нуля.
Открытый ключ устройства передаётся серверу при POST /devices/register в необязательном поле public_key (base64).

=== 10. ЛОКАЛЬНАЯ МОДЕЛЬ РАСПОЗНАВАНИЯ ПЕРЕПИСКИ (требование: работает только на телефоне) ===
- Вся обработка текста идёт на устройстве. Текст сообщений никуда не отправляется, не пишется в лог и не сохраняется на диск. На сервер уходят только pattern_flags и local_score (число 0..1).
- Окно сообщений: последние 10 сообщений от одного отправителя, только в оперативной памяти; очищается через 30 минут без новых сообщений и при закрытии приложения. Источник текста: уведомления (NotificationListenerService).
- Интерфейс на Android: ScamClassifier { fun classify(messages: List<String>): ClassifierResult }, ClassifierResult(score: Float 0..1, flags: List<String>). Реализации: RulesClassifier (ключевые фразы, работает всегда) и OnDeviceModelClassifier (обученная модель). Итоговый score = максимум из двух, flags объединяются. score >= 0.7 считается высоким риском.
- Если файла модели нет или он не загрузился, приложение работает только на RulesClassifier и не падает.
- Уровень 1 (делаем первым, надёжный): TF-IDF по символьным n-граммам (2–5) + линейный классификатор (логистическая регрессия). Экспорт в JSON: словарь, idf, веса, смещение. Инференс на Kotlin без внешних ML-библиотек. Файл assets/scam_model_v1.json.
- Уровень 2 (только если успеваем и он заметно лучше уровня 1): небольшая многоязычная нейросеть, экспорт в TFLite или ONNX. Файл assets/scam_model_v2.tflite (или .onnx). Размер до 50 МБ, ответ до 300 мс на демо-телефоне.
- Нормализация текста одинакова в Python и Kotlin: нижний регистр, схлопывание пробелов, казахские буквы не заменять. Её точное описание пишет роль 3.
- Языки: русский, казахский и смесь, кириллица и латиница.
- Данные: ТОЛЬКО синтетические, помечены source=synthetic, без реальных имён, телефонов, компаний и переписок. Формат JSONL. Один пример = одно окно переписки (3–8 сообщений подряд, соединённых символом перевода строки). Поля: id, text, label (scam|normal), scheme (family_claim|bank_security|prize|investment|code_request|loan|other|none), lang (ru|kk|mix), hard_negative (true|false), source.
- Размер набора: минимум 600 scam и 600 normal, из них не менее 200 hard_negative (настоящие просьбы одолжить деньги, сообщения банков, курьеров, родственников, рассылки). Деление train/val/test = 70/15/15 случайно по id.
- Метрики: recall по scam и доля ложных срабатываний (FPR) отдельно на hard_negative. Цель: FPR на hard_negative не выше 5%. Это цель, а не гарантия. Результаты на синтетических данных нельзя выдавать за качество на реальных переписках.

### Правила работы

1. Сначала контракт, потом ветки и код.
2. Каждый вечер коммит в dev, в main только проверенный код.
3. В день 5 main заморожен, на рабочую версию ставится тег demo-ready.
4. Каждый модуль проверяет другая нейросеть: ошибки, которых не видит автор, находит проверяющий.
5. Сначала ядро (ссылка, тревога, отмена перевода), потом проверка номеров и привратник, потом файлы, и только в конце офлайн-журнал.
6. Перед сливанием прогнать чеклист ниже.
